# SQL 注入检测技能

## 适用条件

- 目标有带参数的 URL（形如 `?id=1`、`?keyword=abc`），或者页面里有表单输入
- 指纹里认出了 PHP / ASP.NET / Java 这类动态后端，说明响应是拼出来的而不是静态文件
- 以下情况跳过本技能：页面纯静态、参数明显只做前端筛选、目标前置 WAF 且已经判定为强拦截

## 测试阶段

1. 收集候选参数：从 URL 查询串和页面表单的 `<input name=...>` 里取
2. 取一次基线响应：请求原始地址，把响应全文留作对照
3. 逐个参数注入显错 payload：`'`、`"`、`')`、`';`、`' AND '1'='2`
4. 判定：注入后的响应里出现数据库报错特征词，而基线响应里没有，说明这个参数有问题
5. 产出：命中参数、命中的 payload、报错原文片段

## 判定标准（什么算漏洞，什么算误报）

**算漏洞**——必须同时满足两条：

- 响应里出现数据库报错原话，例如 `You have an error in your SQL syntax`、`Warning: mysql`、
  `SQLSTATE[`、`ORA-01756`、`unclosed quotation mark`
- 这条报错在基线响应里**不存在**。基线里本来就有，说明是目标自己带着的，不是注入打出来的

**算误报**——以下情况一律不判漏洞：

- 只有状态码变化（500、302 之类），响应里没有报错原话。状态码变化的原因太多了，天气不好也会变
- 页面回显了 payload 本身但没有报错。那说明参数被拼进了前端，压根没进数据库
- 命中 WAF 拦截页（403 且带安全厂商标识）

## 决策原则

- 一个参数确认命中就停手，不再打剩下的 payload。少发请求，也少一份被拦的概率
- 只做显错注入。盲注、时间盲注、堆叠注入 V1.0 不做——靶场噪声低还行，真实站点上全是误报
- 置信度按证据强度给：报错原话清晰可见给 0.85，只捞到片段给 0.6

## 失败处理

- 收集不到任何参数：直接返回空结果并写清楚原因，不要对着首页硬打 payload
- 目标全程超时或连不上：按未测试处理，不重试
- 响应里出现 WAF 拦截特征：立即停掉这个参数剩下的 payload，把已测到的结果原样返回

## 使用示例

一次真实扫描中本技能的轨迹（目标为故意有漏洞的靶场）：

1. 收集候选参数：从首页表单里取出 id、q、file 三个
2. 取基线响应，请求 `http://target/?id=1`，正文是"用户 id=1 的资料"
3. 对 id 注入一个单引号，响应变成
   `You have an error in your SQL syntax ... near ''' at line 1`
4. 基线里没有这句，判定参数 id 存在显错注入
5. 落库漏洞：类型=SQL注入　等级=high　置信度=0.8
   触发载荷：单引号　证据：`near ''' at line 1`
6. 对 q、file 注入同样的载荷没有出现报错，不判漏洞
