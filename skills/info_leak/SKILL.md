# 敏感信息泄露检测技能

## 适用条件

- 只要目标能访问就应该跑一遍。这一类不需要注入点，是"目标自己摆出来"的问题
- 优先级高：备份文件和配置文件外泄往往能直接拿到源码或数据库口令，危害远大于单个注入点
- 没有不适用的场景。哪怕前面所有技能都没找到东西，这一步也可能出结果

## 测试阶段

1. 探高危路径：对着站点根逐个请求下面这些路径，看是否可访问
   - `/.git/config`、`/.svn/entries` —— 版本控制目录，顺着能还原源码
   - `/.env` —— 环境变量文件，通常含数据库口令
   - `/config.php.bak` —— 编辑器留下的配置备份
   - `/backup.zip`、`/db.sql` —— 备份包和数据库导出
   - `/phpinfo.php` —— 环境探针页
2. 看调试信息：页面正文里有没有异常栈、绝对路径、调试开关
3. 看版本号：`Server`、`X-Powered-By` 里有没有带具体版本号
4. 产出：命中的路径 / 调试信息类型 / 泄露版本的响应头，每条都带证据片段

## 判定标准（什么算漏洞，什么算误报）

**算漏洞**：

- 路径返回 200 **且**正文里出现了该文件的内容特征（例如 `.git/config` 里有 `[core]`、
  `.env` 里有 `app_key`、`.sql` 里有 `insert into`）
- 压缩包返回 200 且 Content-Type 是 zip / octet-stream
- 正文里出现异常栈特征，例如 `Traceback (most recent call last)`、`Stack trace:`、
  `Notice: Undefined`、`at java.`
- 响应头里报了带具体版本号的服务端，例如 `Server: nginx/1.24.0`

**算误报**——以下情况一律不判漏洞：

- 只看状态码 200 就判定泄露。**这条最常见的误报来源**：很多站点对不存在的路径统一返回
  200 兜底页，必须同时命中内容特征才算
- 版本号只报到产品名不带数字（例如 `Server: nginx`），那不算版本泄露
- 正文里出现的是普通的业务提示文字，不是调试信息

## 决策原则

- 路径清单保持短小。做大字典爆破请求量上去了，命中率反而低，还容易被封
- 不把"安全响应头缺失"算进本技能。那是指纹技能的角度，两个技能报同一件事会变成重复计数
- 置信度：备份文件或配置文件命中给 0.85；调试信息命中给 0.7；仅版本号泄露给 0.5
  （版本号本身不是漏洞，是下一步的线索）

## 失败处理

- 站点根拼不出来（地址里没有协议头或主机名）：直接返回空结果
- 目标对不存在的路径返回 302 跳转：按未命中处理，不跟随跳转再判
- 响应里出现 WAF 拦截特征：停止后续路径探测，把已测到的结果原样返回

## 使用示例

一次真实扫描中本技能的轨迹（目标为故意有漏洞的靶场）：

1. 对站点根逐个请求高危路径：
   - `/.git/config` 返回 200 且含 `[core]`                     -> 命中
   - `/.env` 返回 200 且含 `APP_KEY`、`DB_PASSWORD`            -> 命中
   - `/backup.zip` 返回 200 且 Content-Type 是 zip             -> 命中
2. 正文里没有异常栈，调试信息一项为空
3. `Server: nginx/1.24.0` 带版本号，版本泄露记一条
4. 落库漏洞：类型=敏感信息泄露　等级=high　置信度=1.0
   证据：`.git/config` 的 `[core]` 行、`.env` 的 `DB_PASSWORD` 行
